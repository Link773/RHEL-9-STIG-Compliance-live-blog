# RHEL-9-STIG-Compliance-live-blog
This is a repository that, despite mostly not working in code, has a README file containing everything I am doing for this project, including any blunders and problems I had to face due to this being my first time creating and hosting a virtual machine. Eventually my goal is to create code using Python and Ansible, as seems to be the standard, to automate the various processes of STIG compliance on this system using the Red Hat Enterprise Linux 9 STIG documentation version 2 Release 10 dated September 30th 2026. However, the initial goal is simply to read, understand, and know how to configure these standards by hand and the benefits and drawbacks of each configuration.

# Graphical Display Manager (Rule SV-257781r991589)
This rule is what made me decide that I need more documents to organize how impactful I deem different rules to the end-user. I am of the understanding that these rulings have their exceptions, especially in cases where they quite literally interfere with the intended uses of the computer itself, such as a rule I saw against VOIP protocols which would obviously be problematic on certain computers.
On a related note, this ruling specifically says to configure RHEL 9 with no graphical interface. This is because the graphical interface creates more vulnerabilities in a system, however I am certain that in some use-cases this can also create problems.
# CTRL-ALT-DEL (Rules: SV-257784r1262100 & SV-257785r1044833)
So I found these rules interesting. CTRL-ALT-DEL is a reboot sequence for Linux systems. With this in mind, I found it rather peculiar that there are rules in STIG requiring the disabling of these hot keys. It strictly has to do with uptime and availability of systems, which makes perfect sense in certain contexts but in others (bare in mind I have minimal knowledge of the systems at play here) it feels like it's at best a nothing-burger and therefore something that makes these rules feel humorous. However, in server environments where uptime would, in theory, be of utmost priority, this ruling makes perfect sense.
# Superuser naming conventions (rule SV-257789r1137691)
This rule is specifically about the naming conventions of the superuser roles and to make sure they're not set to anything obvious like "root" or "admin" or "administrator". Honestly, seeing that rule made me side-eye my VM configurations because, for simplicity of my own access of this VM all the log-in credentials are super obvious (to me anyways) including the passwords. Once again for accuracy sake I did in fact change my superuser username on the system.
